# V7.1 — Handoff: what should change in Codo itself

**Status:** design handoff, not yet applied. Read `public/codo/AGENTS.md` and the three constitution files before touching `public/codo/`; this file is the *specification of intent*, the constitution remains the law of how changes land.

**Sources:** analysis rounds 1–7 (`workshop_docs/versions/V7.0/02…12`), the BRAH paper v6.2 (`paper/index.html`, §6.8 and Table 4 D-1 are the new parts), the root presentation (`presentation/index.html`, پرده‌های سوم و چهارم), and the review log (`workshop_docs/versions/V7.0/13-presentation-issues.md`).

---

## 1. The thesis this encodes

Codo already lives the "free development, strict execution" thesis on its **own pipeline**: anything is allowed during `/idea-core` … `/plan`, then the build runs inside deterministic gates (checklist one item at a time, scenarios as the acceptance contract, deploy only on owner acceptance). What is missing is the **product side**: the app Codo generates does not currently carry a declared security architecture. Whatever the generated service can do at runtime is whatever the build session happened to write — there is no capability partition, no identity-binding rule, no envelope policy, no deterministic fallback path.

The change is therefore: **make the product's runtime policy a declared, reviewable artifact of the pipeline** — authored in the documents, checked by static gates, enforced by generated code. Security must be *specified* the same way the data model is specified, not left as an emergent property of `/build`.

## 2. What changes, by phase

### `/idea-core` — one new business question
"Who calls the product — only humans, or also assistants acting for humans?" If assistants, the product plans for a **delegate principal class** from day one (see §4). This is a business question and belongs there, not in `/plan`.

### `/data-model` → new living document: `docs/living/capabilities.md`
A declarative table of every user-facing action the product exposes:

| action | mode | tier | plain params | envelope params | deterministic trigger |
|---|---|---|---|---|---|
| register | direct | — | course_id | phone, address | menu key «ثبت‌نام» |
| cancel | confirm | master | — | — | button / nonce |
| my_status | read | — | — | — | menu key «وضعیت من» |

- `mode` ∈ {read, direct, confirm} — the producer's dial, per action.
- `tier` on confirm actions ∈ {delegate, master} — who may satisfy the gate (assurance-indexed split authority, paper §6.8).
- `envelope params` — values that must never enter the model's context; they flow through handles.
- `deterministic trigger` — the model-free path every action must also have (menu button, numbered wizard step, typed API call). This is LLM-Zero Completeness: if the model is down, every row is still reachable.

### `/scenarios` — negative scenarios join the contract
The acceptance contract gains a second column: adversarial walks. Minimum set, per product:
- injection in a user message attempts a forbidden action → expected: no such tool exists in the model's world;
- caller asks for another user's record → expected: no identity parameter exists to pass;
- model outage simulated → expected: the menu path completes the same action;
- a confirmation-gated action is attempted without a confirmation → expected: proposal only, no state change.

### `/plan` — `architecture.md` gains the four layers
The generated product is specified as: **(1) transport/auth**, **(2) reference monitor** — binds `peer_id`, `cred_tier`, `delegate_of` from the transport into an immutable context the model cannot see; mediates every tool call; **(3) domain engine** — the deterministic commands; **(4) LLM planner** — text in, tool-call suggestions out, nothing else. The checklist generated by `/plan` lists the static gates below as items.

### `/build` — static gates as checklist items (the compiler for security)
Each gate is a mechanical check over the generated code; failure blocks the item from being ticked:

| gate | rule |
|---|---|
| AST-01 | no capability parameter may name a recipient/identity/raw-secret field (`chat_id`, `peer_id`, `phone`, `token`, …) — identities come from context only. The model-visible convention: calls carry the `CURRENT_USER` placeholder, which the reference monitor substitutes with `Γ.peer_id` at dispatch — the model never emits, sees, or can forge the real id |
| AST-02 | `mode="read"` bodies contain no writes |
| AST-03 | `mode="read"` bodies emit no messages/notifications |
| AST-04 | every user-facing capability has its deterministic trigger from `capabilities.md` |
| AST-05 | every `confirm` capability declares `assurance=` (delegate|master); delegate-reachable code references the master via `ctx.delegate_of`, never a caller field |
| AST-06 | read capabilities touch no private path outside their attenuated context |
| AST-07 | parameters declared as envelopes in `capabilities.md` are typed `HandleRef`, nothing else |
| SEC-01 | no credential literal in any tracked file (extends the existing secrets rule to generated product code) |

### `/test` — owner walks the negative column too
Acceptance means both columns pass: the business scenarios *and* the adversarial ones. `/test`'s rounds format already exists; the negative scenarios run inside it unchanged.

### `/deploy` — unchanged. Runtime policy ships with the code; nothing extra is configured on the server.

## 3. Secrets: two lives, two mechanisms — do not merge them

- **Dev-time secrets** (the builder's keys): stay exactly as they are — `docs/secrets/secrets.local.md`, git-ignored, names-only in code. Codo's existing rule is already correct.
- **Runtime secrets** (what the *product's users* hand the agent — phones, national IDs, addresses, issued tokens): new. They never enter the model's prompt; they are captured before prompt construction into a vault and travel as opaque handles, unveiled only at authorized sinks (the database, the egress wire to the same user). This is the envelope mechanism from paper §7 — generated scaffolding, not a prompt instruction.
- The generated code names three harness-side swap points (the vocabulary the deck demos): `vault()` at capture — plaintext → opaque handle `[h_*]` before prompt construction; `resolve()` at dispatch — handle → plaintext **only for an owner- and destination-authorized** tool argument; `unveil()` at egress — handle → plaintext **only on the output wire to the owning user**. The model passes handles unchanged (`track.enable(num=[h_phone_u3b1])`); model history retains handles forever — plaintext lives at the sinks, never in the context.

## 4. The boss ⇄ employee model — the concrete delegation shape

No A2A endpoint, no new port. In the Codo product:

- The **personal assistant** (the boss) reaches the employee agent over the **same messenger chat port** a human would — it is a *humanoid principal*.
- At onboarding the human master registers the assistant's identity with the service; the employee binds it as a **master-class delegate** — `Γ.delegate_of` points at the master's principal, `Γ.cred_tier` records the grant's level.
- `assurance="delegate"` actions: the assistant may confirm directly, inside its recorded scope (its scope is always ≤ the master's — monotonic attenuation; a delegate credential is narrower than the grant that produced it).
- `assurance="master"` actions: the assistant **relays**. The service emits the proposal to the assistant; the assistant renders its own confirmation surface to the human master on their own channel; the decision returns through the same port. Buttons are never forwarded — each hop renders for its own principal.
- The employee's LLM never sees the credential machinery: binding happens at the transport/auth layer before the model is invoked (paper §6.8, attack class D-1).

## 5. What does **not** change

- No sub-agents, no skills, no framework additions — the constitution's tooling rule holds. All of the above is generated artifacts (one new living document) plus edits to existing command files.
- Files-as-truth, the questions format, rounds, the gate, the session model, `docs/status.md` as master handoff — untouched.
- The delegation model in §4 is *capability*, not new infrastructure: an authenticated chat principal plus a declared tier. Explicitly **not** an A2A endpoint — the analysis settled this (round 7 comment).

## 6. Honest scope note

This moves Codo from "the pipeline is gated, the product is emergent" to "the product's policy is declared and gate-checked." It does **not** claim the full BRAH invariant set — envelopes, post-turn nonces, and the reference monitor are real generated code, and until they exist the product inherits only the weaker baseline (prompt discipline + code review). The handoff orders the work so that the cheapest invariant (capability partition + context-bound identity, items AST-01…05) lands first.
