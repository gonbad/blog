Byzantine-Resilient Agent Harnesses: Enforcing Availability, Integrity, and Confidentiality When Both the Caller and the LLM Planner Are Untrusted

Omid Baharloo

baharloo.omid@gmail.com

Abstract

Large language model (LLM) agents are increasingly given operational authority over multi-tenant services that handle transactions, customer records, and organizational state. Existing defenses either rely on model alignment and prompt-level instructions, or assume a personal-assistant setting in which the party issuing instructions is a trusted owner. In public, multi-tenant deployments neither assumption holds: any anonymous caller may be an adversary, and the LLM planner itself, which is subject to stochastic failure, adversarial manipulation, and observation by its hosting provider, must be treated as an untrusted component. We present the Byzantine-Resilient Agent Harness (BRAH), an architecture that enforces availability, integrity, and confidentiality without depending on model compliance. BRAH rests on three mechanisms. First, LLM-Zero Completeness requires that every business state transition reachable through natural-language interaction is also reachable through a deterministic, model-free port state machine, so that service continues during a total model outage or budget exhaustion. Second, split authority removes all state-mutating capabilities from the planner, which may only propose typed actions that the authenticated principal confirms out of band, while a reference monitor binds every identity and tenant parameter from an immutable execution context. Third, principal-owned, sink-typed opaque handles replace sensitive identifiers in the model’s context, and parameter-free introspection removes existence oracles. We formalize a dual-adversary threat model, state and prove three invariants under explicit assumptions, describe a declarative programming model with compile-time verification gates in a reference runtime, trace four deployment scenarios, and analyze ten classes of attack against the design.

Keywords: LLM agents; prompt injection; reference monitor; confused deputy; object capabilities; multi-tenant security; information-flow control; Byzantine fault tolerance

1. Introduction

Large language models have moved from passive text generators to goal-directed agents that perceive digital environments and execute multi-step workflows. In enterprise settings, such agents are given tool interfaces that let them query relational databases, call third-party REST and Model Context Protocol (MCP) endpoints, manage content systems, and mediate commercial transactions over public messaging platforms.

This shift exposes a structural weakness. An autoregressive model receives control instructions and untrusted data in a single, undifferentiated token sequence. Classical systems separate the two by construction: the Harvard architecture, write-xor-execute page permissions, and parameterized database queries all prevent data from being interpreted as code. An LLM offers no corresponding separation between system prompts, developer policy, conversation history, and external content.

1.1 Model alignment is not a security boundary

Most agent frameworks attempt to prevent unauthorized state changes and data leakage through model-level measures: reinforcement learning from human feedback, instruction-hierarchy fine-tuning, defensive system prompts, and secondary LLM-based filters. Benchmarks of tool-integrated agents show that such measures fail under adaptive attack [9, 10]. Direct injection, indirect injection embedded in retrieved pages or database rows [11], multi-turn social engineering, and syntactic obfuscation all bypass prompt-level guardrails with regularity. Requiring a stochastic model to enforce access-control invariants while it interprets adversarial tokens contradicts two established design principles, separation of duty and complete mediation [5].

1.2 Two threat models

Recent work applies software-security techniques, notably information-flow control (IFC) and capability-based enforcement, to LLM agents [6, 7, 8]. These systems are designed for what we call the personal-assistant threat model, which rests on four assumptions. (i) The prompter is a single authenticated, trusted owner. (ii) The adversary is a third party that plants instructions in passive data fetched during execution, such as a document or an email body. (iii) The inference provider is trusted, so confidential documents may be placed in the model context in plaintext. (iv) Availability is secondary to fail-closed behavior, so halting when a policy is violated or the model is unreachable is acceptable.

Public service agents, such as event-registration desks, customer-support agents, and multi-tenant brokerage platforms, operate under a different model, the public multi-tenant service-agent threat model, in which all four assumptions fail together. Any anonymous user of a messaging network can open a session, so the conversational caller is the primary adversary and may attempt to read other customers’ records, manipulate prices, or trigger unauthorized broadcasts. Because the planner processes the caller’s input directly, and is itself subject to hallucination and jailbreaking, it must be modeled as an untrusted, possibly compromised component. Cloud-hosted inference spans third-party jurisdictions and proxies, so sending regulated personal data to the model in plaintext is itself a disclosure. Finally, availability is a business requirement: a commercial agent cannot stop working because a provider suffers a network partition, returns gateway errors, or because an abusive caller exhausts the token budget.

1.3 Contributions

Rather than strengthening prompt compliance, BRAH encapsulates the untrusted planner inside a deterministic reference monitor. The contributions are as follows.

  1. A dual-adversary service threat model in which the external caller Acaller and the internal planner ALLM are both untrusted and may collude (Section 3).
  2. LLM-Zero Completeness for availability: every business transition that can be reached through model-assisted interaction has an equivalent path through deterministic ports that never invokes the model (Section 5).
  3. Split-authority proposals and context-bound proxies for integrity: state-mutating tools are removed from the planner’s schema, mutations become typed proposals ratified by the authenticated principal, and all ambient identifiers are injected by the reference monitor (Section 6).
  4. Principal-owned, sink-typed opaque handles for confidentiality: a tokenization vault, two-tier ingress scrubbing, and zero-argument introspection prevent provider-side disclosure and cross-user existence oracles (Section 7).
  5. A declarative programming model with compile-time static checks that make insecure tool definitions unregisterable (Section 8), together with an analysis of four deployment scenarios and ten attack classes (Sections 9 and 10).

2. Background and Related Work

2.1 Classical foundations

BRAH adapts four results from systems security. Anderson’s reference monitor concept [1] requires that a mediating mechanism be tamper-proof, invoked on every access (non-bypassable), and small enough to be verified. Hardy’s confused deputy problem [2] describes how a program holding ambient authority can be induced by a less-privileged caller to misuse it. In a conventional agent, tools whose target parameters (recipient, tenant, record) are chosen by the model make the agent a confused deputy. Object-capability security [3] removes ambient authority by requiring that a subject hold an unforgeable reference that both designates an object and authorizes a set of operations; BRAH transfers this idea to natural-language runtimes through principal-owned, sink-restricted handles. Denning’s lattice model of information flow [4] provides the vocabulary of confidentiality and integrity labels used to reason about flows toward public sinks and from low-integrity sources.

2.2 LLM agent security architectures

Benchmarks such as InjecAgent [10] and AgentDojo [9] show that prompt-level defenses fail against adaptive indirect injection, and recent work has moved toward system-level isolation. CaMeL [6] derives control and data flows from the user’s trusted query. A privileged LLM compiles the query into a restricted program, a quarantined LLM without tool access parses untrusted data into typed values, and a custom interpreter tracks provenance and enforces capability policies at tool calls. The authors report solving 77% of AgentDojo tasks with provable security, against 84% for an undefended system. The guarantee presupposes a trusted initial query; if that query comes from an adversary, the privileged model compiles the attacker’s instructions into the plan. In addition, the quarantined model sees the raw data it parses, and a policy violation causes execution to stop.

FIDES [7] propagates confidentiality and integrity labels dynamically across planner turns and provides a selective hiding primitive that replaces confidential values with symbolic variables in the model context. It assumes a trusted task initiator and does not address out-of-band principal confirmation or operation when the planner is unavailable. IsolateGPT [8] isolates third-party LLM applications in separate processes mediated by a central hub, which limits cross-application contamination for a single user, but it does not address shared multi-tenant business state manipulated by anonymous callers.

3. System Model and Threat Model

To state guarantees that do not depend on stochastic model behavior, we model the service agent as a state-transition system mediated by a deterministic reference monitor.

3.1 Notation

A multi-tenant service agent is the tuple Ssys = ⟨S, P, Γ, C, T_M, M, H, Σ⟩. The set of authenticated principals is S = Suser ∪ Sop ∪ Sbrk ∪ Sadm, comprising end users (customers, registrants, channel readers, or programmatic personal assistants), tenant operators (business owners who configure and supervise an isolated tenant instance), wholesale brokers (parties authorized to create tenant instances and settle wholesale usage), and the infrastructure administrator.

Events enter through four typed ingress ports, P = {Pbot, Pacct, Papi, Pllm}. The port Pbot carries official messenger-bot webhooks, which deliver verifiable sender identifiers, structured contact cards, and inline-button callback payloads. The port Pacct carries personal-account session streams (for example MTProto-based clients or WhatsApp session gateways), which deliver text and media messages authenticated by platform peer identifiers but offer no structured interface elements. The port Papi carries structured HTTP and MCP endpoints, authenticated by bearer tokens whose SHA-256 digests are stored server-side. The port Pllm is the untrusted output stream (text and tool calls) returned by the inference gateway.

On an event from any port p ∈ P ∖ {Pllm}, the harness creates an immutable execution context bound to a turn:

Γ = ⟨run_id, tenant_id, port, peer_id, role, σdb⟩
(1)

where tenant_id identifies the isolated tenant instance, peer_id is the identity of the caller as verified by the transport, and σdb is the database state snapshot. The context is held in coroutine-local runtime storage. The planner M has no read or write access to Γ and cannot forge or override any of its fields.

The domain engine exposes a finite set of deterministic commands C = Cread ∪ Cmutate, such as querying public information, registering an attendee, issuing an invoice, or approving a listing. Each command c ∈ C is guarded by a deterministic predicate Authz(s, Γ, c, args) ∈ {true, false}. The untrusted planner is a function M : Hsan × T_M → Text ∪ Aproxy. It receives only a sanitized, pseudonymized history Hsan and an attenuated proxy toolset T_M. Each proxy tool t̃ ∈ T_M either executes a context-bound read in Cread or emits a non-executing proposal Π(c, args) for some c ∈ Cmutate. The reference monitor H mediates every ingress event, model invocation, and egress side effect. It maintains the opaque handle vault

Σ : R → Vsecret × Kind × TenantId × OwnerPeer × 2T
(2)

which maps unguessable handle strings h ∈ R to the underlying sensitive values, with the set of tools (sinks) permitted to dereference each handle.

3.2 Dual-adversary model

The first adversary, the untrusted external caller Acaller, interacts over Pbot, Pacct, or Papi and controls all inbound payloads. It may send direct injections, spoof system roles, or embed instructions in forwarded messages, documents, or URLs. Its goals include cross-peer and cross-tenant access (peer_id′ ≠ Γ.peer_id or tenant_id′ ≠ Γ.tenant_id); unauthorized mutations such as registering without payment, obtaining discounts outside the operator’s negotiation limits, or forging payment confirmations to the operator; and sending messages to third parties. It may also mount denial-of-wallet attacks by flooding the agent with token-intensive requests to exhaust a tenant budget or the host’s inference quota.

The second adversary is the Byzantine planner [12] ALLM, which represents the model together with its hosting infrastructure in two roles. As an active subverter, whether through Acaller’s injections, poisoned weights, or ordinary hallucination, the model may emit arbitrary tool calls with fabricated arguments, supply another user’s identifier or handle, produce deceptive text next to a legitimate confirmation control, or claim that an operation has completed. As a passive observer, the cloud provider, network relays, and logging pipelines can read every token of the prompt. Any plaintext personal data, credential, or platform identifier in the prompt is therefore assumed to be disclosed. The two adversaries may collude.

We assume that transport-level authentication (Layer 1) is not compromised, that the reference monitor and the domain engine are correctly implemented, and that cryptographic primitives and the random-number generator behave as specified.

3.3 Security objectives

A harness is Byzantine-resilient if it enforces three invariants under this model.

Availability invariant (A). Every domain command c ∈ C assigned to a principal role remains executable, with latency bounded independently of M, when M returns arbitrary errors, times out, or is unreachable.

Integrity invariant (I). No state-mutating command c ∈ Cmutate and no cross-peer outbound transmission can be executed by M directly. Every mutation requires an explicit confirmation originating from the authorized principal over a deterministic port, with all tenant and identity parameters taken from Γ.

Confidentiality invariant (C). For the protected classes of secrets Vsecret (Section 7), the mutual information between the prompt observed by M and Vsecret is zero, I(Prompt; Vsecret) = 0, and no caller s can infer or dereference any datum owned by a principal s′ ≠ s.

4. Architecture

BRAH replaces the usual topology in which the model acts as controller with a three-layer reference monitor. The planner is an advisory leaf node outside the trusted computing base (TCB). Figure 1 shows the layers and the data crossing each boundary.

4.1 Layer 1: ingress authentication, port normalization, and tokenization

Layer 1 terminates network connections from messaging servers and API clients and performs three operations before any downstream logic runs. First, it authenticates at the transport level. For bot webhooks it validates a secret path component or header known only to the harness and the messaging platform and extracts the unforgeable sender identifier, any button callback payload, and any verified contact card. For personal-account streams it binds the sender’s platform peer identifier to the account session wired to the tenant. For structured API and MCP ports, authentication middleware extracts the bearer token, computes its SHA-256 digest, compares it with the stored digest, and rejects failures with 401 Unauthorized before any tool function is reached.

Second, Layer 1 intercepts deterministic triggers. If an authenticated event is an inline-button callback, a slash command, or a numeric state-machine code (including a confirmation nonce), the model is bypassed and the command is dispatched through Layer 2 to Layer 3. Third, if the event is free text for the model, Layer 1 applies the two-tier PII scrubber (Section 7.1), replacing structured contact payloads and pattern-matched digit sequences with opaque handles h ∈ R stored in Σ.

4.2 Layer 2: reference monitor and context binder

Layer 2 is the core of the TCB. It instantiates Γ and enforces three mediation rules. Implicit context binding: whenever a tool or command is invoked, Layer 2 reads tenant_id, peer_id, and, where applicable, the broker identifier from Γ and injects them into the function’s typed context parameter. These fields do not appear in the schema presented to the model, so the model cannot specify or alter tenant or recipient boundaries. Split-authority gate: direct principal triggers arriving on Pbot, Pacct, or Papi may invoke authorized commands in Cmutate, while calls originating from Pllm are restricted to read-only queries in Cread and non-mutating proposal generators Π(c, args). Scoped handle dereferencing: before any handle argument reaches Layer 3, Layer 2 checks it against Σ, verifying that it belongs to the current tenant, is owned by the current caller, and is permitted for the target sink (Equation 4).

4.3 Layer 3: deterministic domain engine

Layer 3 contains the domain logic, persistence models, append-only financial ledgers, and outbound notification routers. It contains no model calls. Its inputs are commands whose parameters were validated and bound by Layer 2, and its outputs are state changes and notifications generated by code.

4.4 Administrative planes and delegated authority

Authority over the system is partitioned across four planes, each with its own credential type and fixed tool schema, so that compromise of one credential does not confer the authority of another. The administration plane serves the infrastructure owner: it manages brokers and their credit limits, exposes usage metrics, and permits row-capped, redacted, read-only diagnostic queries; every mutating call requires a two-step confirmation token. The broker plane allows a broker to inspect a manifest, ask read-only pre-sales questions, create isolated tenant instances, set per-tenant spending ceilings, suspend or resume tenants, and audit wholesale payables. The operator plane allows a tenant operator to configure persona and behavior, add knowledge entries, wire platform credentials, configure notifications, review pending approvals, and read reports, together with any role-specific management tools. The end-user plane is the surface used by customers through messenger bots, personal-account channels, companion web services, or programmatic assistants.

Two properties follow. First, because every configuration action is available through a deterministic management interface, administrative continuity does not depend on the model. Second, a deterministic wholesale ledger enforces the per-tenant spending ceiling set on the broker plane and halts a tenant the moment its usage reaches the ceiling, which bounds the loss caused by a buggy or malicious tenant agent regardless of what the planner does.

5. Pillar I: Availability through LLM-Zero Completeness

A common failure mode in agent engineering is LLM-monolithic coupling, in which the model sits on the critical path of every interaction. If the provider is unavailable, throttles requests, or responds slowly, or if an attacker consumes a tenant’s token budget, such an agent stops responding altogether. For a commercial service this is a violation of basic availability requirements.

5.1 Definition

Definition 1 (LLM-Zero Completeness). Let Σbiz denote the domain state space of a tenant instance and let Δ : Σbiz × C → Σbiz be the deterministic transition function over commands. A harness satisfies LLM-Zero Completeness if and only if, for every reachable transition σ c→ σ′ that can be assisted or proposed by the planner M, there is a finite input sequence p over the deterministic ports Pdet = Pbot ∪ Pacct ∪ Papi that produces the same transition without invoking M:

∀(σ, c) ∈ Σbiz × C,  ∃  p ∈ Pdet*    such that    Exec(p, σ) = Δ(σ, c) ∧ Calls(M) = 0
(3)

Under this definition the model is never the exclusive executor of a business capability. Its role is to help users who write in natural language discover commands and pre-fill their parameters for ports that are executable without it.

5.2 Deterministic port state machines

Because transports differ in their interface primitives, Layer 1 implements one deterministic port state machine (port-FSM) per port class, each exposing the full command set without invoking M. On bot ports, every command declared as principal-triggered is compiled into an interactive menu button and a slash-command handler. In an event-registration agent, for example, the menu offers buttons for event details and remaining capacity, a verified FAQ, registration, sharing a verified contact, and payment. Each button produces a signed callback that Layer 1 routes directly to Layer 3.

On personal-account channels, which have no inline buttons, Layer 1 maintains a per-peer finite-state automaton driven by numeric codes or keywords. Sending 0 returns a numbered directory of services, and replying with a number advances a deterministic dialogue that collects the required fields and confirms the action with a four-digit nonce. On structured API and MCP ports, every capability is a typed JSON-RPC tool that deterministic scripts or external orchestrators can call without conversational mediation.

5.3 Unified command bus

Dual-mode systems risk logic divergence between manual menus and model-assisted flows. BRAH removes the risk by routing all execution paths through a single command bus in Layer 3. A registration may be triggered by an inline button, by a numeric code followed by a nonce, by a programmatic call from a personal assistant, or by confirming a card that the model proposed. All four paths invoke the same principal-command function, so authorization, validation, and side effects are implemented once.

5.4 Circuit breaker and quotas

When a user sends free text instead of a menu command, Layer 2 mediates the call to M behind two guards. First, a circuit breaker traps model failures. If the gateway exceeds a timeout (8 s in the reference configuration), returns a 5xx or 429 status, or produces output that fails schema validation, Layer 2 replies with the deterministic menu and a notice that natural-language assistance is temporarily unavailable. Second, per-peer sliding-window quotas bound token consumption by a single caller: at most NLLM natural-language turns per hour (12 in the reference configuration) and at most Ktools proxy calls per turn (4). When a peer exceeds NLLM, Layer 1 switches that peer’s session to menu-only mode, which stops model token consumption while leaving every command available. A legitimate customer who reaches the limit can therefore still complete registration and payment.

5.5 Availability theorem

Theorem 1 (Availability under planner failure). Consider a service agent built on BRAH that satisfies Definition 1, and assume that the deterministic components (transports, Layers 1 to 3, and the database) are available. For any failure state of the planner M, including complete disconnection, arbitrary malformed output, or per-peer quota exhaustion, the set of executable transitions Δ(σ, c) for all authorized principals is unchanged, and each is reachable within a time bound that does not depend on M.

Proof. Take any authorized command c ∈ C and state σ ∈ Σbiz. By Definition 1, the command compiler has registered a deterministic trigger sequence p ∈ Pdet* mapped to c on the command bus. When principal s submits p through a bot callback, a numeric code, or an API call, Layer 1 authenticates s, matches p against a trigger table in O(1) time, and dispatches c through Layer 2 to Layer 3 without invoking M. If instead s submits free text while M is unreachable, malformed, or rate-limited, Layer 2 traps the fault within the timeout and returns the menu that lists p. In both cases s executes Δ(σ, c) with Calls(M) = 0. ■

The theorem concerns the model as a point of failure. It does not protect against failures of the deterministic components, which are part of the TCB and are addressed by conventional redundancy. The coverage premise of Definition 1 is checked at build time (rule AST-04, Section 8.3).

6. Pillar II: Integrity through Split Authority and Context-Bound Proxies

Integrity requires that no unauthorized state change, financial charge, or cross-user communication can occur even when an attacker has complete control over the model’s output.

6.1 The confused deputy in agent tool execution

Conventional tool-calling frameworks expose general-purpose functions to the model, for example send_message(chat_id, text), query_database(event_id, query), or register_user(event_id, name, phone). The harness holds the global credentials, so every parameter in a tool’s schema is under the model’s control. After an injection, the subverted model can supply another user’s chat_id or another tenant’s event_id, and the harness executes the request with its own ambient authority. This is the confused deputy [2].

6.2 Context-bound capability proxies

BRAH forbids ambient target parameters in the planner’s toolset: no tool exposed to M may accept a parameter that designates a message recipient (chat_id, peer_id, user_id), a tenant boundary (tenant_id, broker_id), or a cross-tenant resource (event_id). The model receives narrow proxies such as reply_text_to_current_user(text) and search_current_event_kb(query). When M calls a proxy, Layer 2 reads the context Γ and rewrites the call deterministically:

search_current_event_kb(q)  →  SELECT * FROM kb WHERE tenant_id = Γ.tenant_id AND match(q)
reply_text_to_current_user(m)  →  transport.send_text(recipient = Γ.peer_id, text = strip_controls(m))

Because M cannot alter Γ, a prompt-injected model has no means of addressing a message to another user or reading another tenant’s knowledge base.

6.3 Split-authority action proposals

Context-bound proxies make reads and plain replies safe, but they do not suffice for high-consequence mutations c ∈ Cmutate that alter business records, create financial obligations, or trigger external workflows. If M held a tool such as confirm_my_registration(), even one bound to Γ.peer_id, a hallucinating or injected model could register a user who had only asked a question, or attach fabricated parameters to the user’s profile.

BRAH therefore applies split authority: commands in Cmutate are never members of T_M. For each mutating command that permits model assistance, the runtime synthesizes a proposal tool propose_<c>(args), the proposal Π(c, args). Calling it changes no state. Layer 2 validates the arguments, computes any monetary quote in deterministic code, stores an inert proposal record, and renders a confirmation element to the authenticated human principal. The mutation Δ(σ, c) is executed in Layer 3 if and only if that principal activates the confirmation button (on Pbot) or returns the post-turn nonce (on Pacct).

6.4 What-you-see-is-what-you-sign binding and turn preemption

An early design let the model emit free text together with a button-rendering tool. That allowed UI phishing (attack class I-1): a subverted model could write “Click below to download the free brochure” above a button that commits a paid registration. It also allowed the model to alter draft fields before confirmation (class I-3).

BRAH closes both paths with WYSIWYS draft binding and turn-level message preemption. Whenever M calls a proposal tool, Layer 2 discards all free text that M produced in that turn, so the model cannot frame or disguise the confirmation. Layer 2 then builds the entire confirmation message and button label deterministically from the stored proposal record and the pricing engine. The card begins with a fixed header (“Official confirmation form: the button below finalizes the details listed here”), lists every bound parameter (full name, masked verified phone number, event title, exact price), and carries a descriptive button label such as “Confirm registration: price 2,000,000 units”. Generic labels such as “OK” are rejected by the command compiler.

6.5 Post-turn egress nonces on text-only channels

On personal-account channels there are no inline buttons. If confirmation used a static code (“send 9 to confirm”), a prompt-injected model could use its text reply to socially engineer the user (“to receive a free gift, reply 9”) into authorizing a mutation.

BRAH instead uses dynamic post-turn egress nonces. When M calls a proposal tool on such a channel, Layer 2 ends the model turn immediately. Only after the turn has finished does Layer 2 draw a fresh nonce from a cryptographic generator,

nauth ←R {1000, …, 9999}

store ⟨prop_id, nauth, expires_at = t + 300 s, attempts = 0⟩, and append a system footer to the card at the egress boundary (“[System]: to finalize this action, send the code 4829”). The nonce is never written to the conversation history visible to M, so the planner has no information about it. Three consecutive wrong inputs invalidate the proposal, which limits guessing.

6.6 Separating system-fact notifications from customer escalations

If the agent has a general tool for messaging the operator’s notification channel, a compromised model can fabricate a payment or registration confirmation during a customer conversation and thereby induce the operator to deliver goods or services without payment (class I-2). BRAH therefore separates the two kinds of message. Official notifications of state changes, such as confirmed registrations, verified payments, newly submitted listings, or budget alerts, are emitted only from principal-command handlers in Layer 3 after the database commit, and the planner has no tool that can produce one. To let the agent hand an unanswerable question to the operator, the planner is given only escalate_question_to_operator(summary). That tool is limited to one open escalation per customer thread, and Layer 2 prefixes every escalation with a fixed banner stating that the text is an unverified claim by the customer and carries no system or financial confirmation.

6.7 Integrity theorem

Theorem 2 (Integrity against planner subversion). Consider a service agent that implements context-bound proxies, split-authority proposals, WYSIWYS turn preemption, and post-turn egress nonces, and assume that Layer 1 transport authentication is not compromised. The probability that an active Byzantine planner M executes an unauthorized state mutation c ∈ Cmutate, or transmits a message to a peer peer_id′ ≠ Γ.peer_id, is 0 on Pbot and Papi. On Pacct it is at most 3/9000 ≈ 3.3 × 10−4 per proposal.

Proof. First, for every proxy tool t̃ ∈ T_M, recipient and tenant identifiers are absent from the schema and are bound by Layer 2 from Γ, so the probability of a cross-peer dispatch or a cross-tenant query is 0. Second, since Cmutate ∩ T_M = ∅, the planner can only invoke Π(c, args). On each such call, Layer 2 discards the planner’s free text and emits a deterministic WYSIWYS card. On Pbot and Papi, executing c requires an authenticated callback bound to the principal’s session, which M cannot produce, so the probability is 0. On Pacct, execution requires the principal to return nauth, which is drawn after the planner’s turn has ended. Hence I(M; nauth) = 0, and turn preemption removes any concurrent text through which M could solicit a code. Any code that M causes to be submitted must therefore be a blind guess, and with a lockout after three attempts the probability of matching a uniformly drawn four-digit nonce is at most 3/9000. ■

The theorem bounds what the planner can cause. It does not address a human principal who confirms a correct card on the basis of a mistaken understanding (Section 11).

7. Pillar III: Confidentiality through Opaque Handle Tokenization

Confidentiality requires that sensitive user data and tenant secrets remain hidden from other callers (Acaller) and from the cloud model provider (ALLM). Earlier envelope-and-redaction approaches protect individual values but do not give a general model in which the planner can reason over metadata and pass references between tools without observing the underlying data or creating cross-user oracles. We define such a model here.

7.1 Two-tier ingress scrubbing

If an agent tokenizes a phone number only when the user presses a platform “share contact” button, a bypass is obvious (attack class C-2): a user who types the digits into the chat sends them to the model in plaintext. Layer 1 therefore scrubs every inbound update before it is stored or serialized into a prompt.

Tier 1 handles cryptographically verified platform contacts (kind phone_verified). When a user presses the platform’s contact-request button, or sends a contact card matching the sender identifier, Layer 1 intercepts the structured payload outside the model, stores the number in the vault, and inserts a synthetic event into the transcript that carries only a handle. Tier 2 is a pre-prompt pattern scrubber for free text (kinds phone_unverified, national_id, card, iban, and credentials). It first normalizes decimal digits from the Latin, Arabic-Indic, and Extended Arabic-Indic Unicode blocks, then scans for mobile numbers, national identification numbers, payment-card numbers, bank-account identifiers, and API tokens. Each match is removed from the message before logging or model transit, stored in the vault, and replaced inline by a typed handle (for example, “my number is [ref_phone_unverified_u3b1]”). A command that requires a phone_verified handle will not accept a handle of kind phone_unverified, so the planner can tell the user to press the official contact button without ever having seen the digits.

7.2 Principal-owned, sink-typed capability handles

A naive tokenization scheme that keeps a flat table from handle to plaintext is vulnerable to confused handle injection (class C-1). If user B learns or guesses a handle that belongs to user A and asks the model to act on it, a tool wrapper that dereferences the handle discloses or corrupts A’s record. BRAH defines each vault entry as a five-tuple object capability,

Σ(h) = ⟨vplaintext, kind, tenant_id, owner_peer, Psinks⟩

and Layer 2 applies the following three-way dereferencing rule whenever a tool t attempts to resolve h under context Γ:

{
Dereference(h, Γ, t) = vplaintext   if Σ(h).tenant_id = Γ.tenant_id ∧ Σ(h).owner_peer = Γ.peer_id
                                                   ∧ t ∈ Σ(h).Psinks
Dereference(h, Γ, t) = ⊥ (raise HandleAccessViolation)   otherwise
(4)

The sink set Psinks restricts where an unveiled value may flow. A customer’s verified phone handle may be permitted for the database insert and for the notification to the operator’s private channel, but never for a message sent to an external chat and never in a tool result returned to M.

7.3 Zero-argument state introspection

Scrubbing and ownership checks still leave a side channel, the existence oracle (class C-4). Suppose a customer-facing tool accepts a phone handle, as in check_registration_status(phone_handle). An attacker types a victim’s number into the chat, Layer 1 turns it into a handle owned by the attacker’s own session, and the model passes the handle to the tool, which reveals whether the victim is registered.

BRAH eliminates the oracle by requiring that customer-facing status tools take no identity or handle argument (get_my_registration_status()). Layer 2 binds the query to the caller’s authenticated transport identity (WHERE tenant_id = Γ.tenant_id AND peer_id = Γ.peer_id). Search across attendees is available only on the operator plane.

7.4 Deterministic metadata pseudonymization

Platform-native identifiers (chat, user, and channel identifiers) are also withheld from the planner, since they allow correlation across sessions. Layer 2 removes them before building the prompt and substitutes constant symbolic names for the caller, the operator, and the tenant. Outbound tool calls resolve these symbols to physical identifiers only inside Layer 2’s egress adapter.

7.5 Confidentiality theorem

Theorem 3 (Confidentiality and non-interference). Consider a service agent that implements two-tier ingress scrubbing, five-tuple principal-owned handles, zero-argument introspection, and metadata pseudonymization. Let Vsecret denote the values matched by the recognizers of Section 7.1 together with platform identifiers. Then (1) no value in Vsecret enters the context window of M, and (2) for any two distinct end users u1 ≠ u2, the observable outputs of u1 do not depend on the private records or handles of u2.

Proof. (1) Every ingress payload passes through the scrubber and the pseudonymizer before prompt construction. Structured contacts, pattern-matched digit sequences, and platform identifiers are replaced by handles drawn from a cryptographic random generator, or by constant symbols. Since the replacement is independent of the plaintext, I(Prompt; Vsecret) = 0 for this class of values. (2) Suppose u1 tries to use a handle h2 created in u2’s session. The attempt fails the dereferencing rule (4), because Σ(h2).owner_peer = u2 ≠ Γ.peer_id = u1. Suppose u1 tries to probe u2’s registration state. The only available tool is get_my_registration_status(), which takes no argument and filters on peer_id = u1. The outputs available to u1 are therefore statistically independent of the state of u2. ■

The theorem is scoped to structured identifiers. It makes no claim about unstructured personal information in free text, which is discussed in Section 11.

8. Declarative Programming Model and Static Verification

Security architectures often fail in practice because they depend on application developers to write permission checks by hand in every tool function. In BRAH the invariants are enforced by the framework’s compiler and runtime, so that an insecure tool cannot be registered. The reference implementation is called codo-core.

8.1 Principal commands and advisory tools

Developers never register raw functions on the model. The declarative API offers two decorators that wire all three pillars automatically.

from codo_core import BoundCtx, HandleRef, PrincipalCtx, llm_tool, principal_command

@principal_command(
    slug="confirm_registration",
    title="Finalize event registration",
    menu_button="Register for the event",
    account_menu_key="3",
    allow_llm_proposal=True,
)
async def confirm_registration(
    ctx: PrincipalCtx,
    full_name: str,
    phone: HandleRef["phone_verified"],
) -> dict:
    reg_id = await ctx.db.registrations.create(
        tenant_id=ctx.tenant_id,
        peer_id=ctx.peer_id,
        full_name=full_name,
        phone_number=phone.unveil_for("db_register"),
    )
    await ctx.notify_operator(
        f"New confirmed registration: {full_name}, "
        f"phone {phone.unveil_for('operator_notify')}"
    )
    return {"status": "confirmed", "registration_id": reg_id}

@llm_tool
async def search_event_faq(ctx: BoundCtx, query: str) -> list[dict]:
    return await ctx.db.knowledge.search(tenant_id=ctx.tenant_id, query=query)

From the single @principal_command declaration the framework synthesizes four security-enforcing artifacts. Under Pillar I, it mounts a deterministic menu handler on Pbot (a button whose callback is cmd:confirm_registration) and binds the account-channel automaton to menu key 3 on Pacct. Under Pillar II, it generates the attenuated proposal proxy propose_confirm_registration(full_name, phone_handle) for T_M, which withholds direct execution from the model and enforces WYSIWYS rendering and post-turn nonce verification. Under Pillar III, Layer 2 verifies, before the command body runs, that phone_handle resolves in Σ to a handle of kind phone_verified owned by ctx.peer_id within ctx.tenant_id.

8.2 Typed context injection and schema omission

To build the tool schema for T_M, the framework inspects each function signature, removes the leading context parameter (BoundCtx or PrincipalCtx), and converts every HandleRef[Kind] annotation into a plain string parameter <name>_handle that carries the schema pattern ^ref_[a-z_]+_[a-z0-9]{4,16}$. At call time Layer 2 injects the context from the coroutine-local variable. The omitted parameters therefore do not exist from the model’s point of view.

8.3 Static verification gates

At build and test time, the checker parses each source file into an abstract syntax tree and enforces four mandatory rules (Table 2).

Table 2. Static verification rules. A violation of any rule fails the build and blocks deployment.
IDRuleCondition checked
AST-01Ambient identifier banNo parameter of an @llm_tool function is named in the forbidden set {chat_id, peer_id, user_id, recipient, tenant_id, broker_id, event_id}.
AST-02Plaintext PII parameter banNo @llm_tool or @principal_command parameter whose name matches *phone*, *mobile*, *national_id*, *card*, or *iban* is typed as anything other than HandleRef[...].
AST-03Planner mutation banThe body of an @llm_tool function contains no database write calls (insert, update, delete, session.add, .create(), .update()) and no operator-notification calls.

AST-01 to AST-03 establish the premises of Theorems 2 and 3 at the level of code, and AST-04 establishes the coverage premise of Definition 1.

8.4 Prompt-based enforcement is not accepted as evidence

The development process applies a corresponding rule to security requirements. Each threat in a project’s threat register must be mapped to a deterministic mechanism in Layer 1, 2, or 3 and to an automated test. An entry whose stated enforcement is “prompt” or “model instructions” for a confidentiality, integrity, or availability requirement is treated as unmet. When a developer requests a design that violates a BRAH invariant, such as autonomous payments without human confirmation or spending limits, the tooling issues an explicit warning describing the resulting confused-deputy and exfiltration exposure and requires a recorded acceptance of the risk before proceeding.

9. Case Studies

To show that the design applies across commercial roles without special-casing, we trace it through four deployment scenarios.

9.1 Event registration and ticketing

The first scenario is a multi-tenant agent that answers questions about an event, negotiates discounts within an operator-defined band, registers attendees, collects payment, and notifies the organizer, through an official bot, personal-account channels, and an API. 9.2 Scheduled content publication

The second scenario is an agent that wakes on operator-configured schedules, fetches news from external sources, writes articles for a companion web site, and posts summaries to the operator’s channels. Fetched pages are untrusted and may contain indirect injections intended to make the agent publish a malicious link or post to an attacker’s channel. Fetched content is wrapped in randomized delimiter tags, output is constrained to a typed schema in which every citation URL must belong to the set of URLs actually fetched in that run, and the publishing tool accepts no destination argument: Layer 2 reads destination channels and sealed publishing credentials from the tenant’s account configuration. Under Pillar I, an operator who wants to pause publication, change the schedule, or order an immediate post during a model outage does so deterministically through the operator plane.

9.3 Customer support over personal-account channels

The third scenario is a support agent operating on the operator’s own messaging accounts, with inbound-message debouncing (a short quiet window with a hard cap). Layer 1 binds each turn to (tenant_id, platform, peer_id). A design with a history-search tool that spans all peers was rejected because it permits cross-customer leakage; customer-facing memory tools (get_my_chat_history, send_reply) take no peer parameter. When the operator replies to a customer directly from the shared account, Layer 1 detects an outbound message not authored by the harness, marks the thread as under human control so that automatic replies stop, and proposes a generalized FAQ entry through a principal command that requires the operator’s confirmation before the entry enters tenant-wide knowledge.

9.4 Brokerage marketplace

The fourth scenario is a marketplace with two groups of users: agent developers (supply) and operators who rent agents (demand). When a developer submits an agent’s broker endpoint and credential, the Layer 1 scrubber seals the credential in the vault, so it never enters the marketplace model’s context. A principal command validates the target’s manifest, stores the listing in an unverified state, and sends a deterministic alert to the marketplace owner. The planner has no tool that moves a listing from unverified to approved; only the owner can do so, through an operator-plane tool. On the demand side, when an operator pays a rental fee (for example 500,000 units), the deterministic payment handler creates the tenant instance and sets its wholesale spending cap (for example 400,000 units) on the target agent’s broker plane. Even if the developer’s agent is faulty or malicious, the wholesale ledger halts the tenant when usage reaches the cap, which protects the marketplace’s credit line.

10.1 Interactions among defenses

Three interactions between mechanisms deserve explicit discussion. The first concerns integrity and confidentiality (C-1, C-2, C-4). Consider an architecture that scrubs phone numbers (C-2) but has neither principal-owned handles (C-1) nor zero-argument introspection (C-4). When an attacker types a victim’s number, the scrubber converts it into a handle owned by the attacker’s session. If the status tool accepted a phone handle, the ownership check Σ(h).owner_peer = Γ.peer_id would pass, because the attacker typed the digits in the attacker’s own session. Two measures together close the oracle: typed digits are labeled phone_unverified and cannot be used for registration, and status queries are bound to Γ.peer_id instead of to any handle.

The second concerns turn-level preemption (I-1, I-3). Common human-in-the-loop frameworks allow the model to emit an explanatory string in the same turn as a deferred approval request. A subverted model can use that string to misdescribe what approval does. By suppressing the model’s text whenever a proposal is emitted and generating the whole card from the validated proposal, BRAH ensures that the principal sees only system-generated parameters.

The third concerns quotas and completeness (A-1, A-2). In a conventional chatbot, rate-limiting a user after a number of messages can block a legitimate customer from completing a purchase. Because BRAH satisfies LLM-Zero Completeness, switching a rate-limited session to menu-only mode never blocks a conversion: the customer still has the deterministic menu for registration and payment, at no token cost.

11. Discussion and Limitations

11.1 Conversational fluidity versus fail-safe defaults

Removing mutating capabilities from the planner and requiring out-of-band confirmation introduces an additional step before high-consequence actions. This is acceptable for services that create legal commitments, process payments, or publish to organizational channels, and the cost is a deliberate one: the design applies the principle of fail-safe defaults [5], under which every mutation stays an inert proposal until an authenticated principal ratifies it. For low-stakes conversational applications the friction may not be warranted, and the read-only parts of the architecture can be used on their own.

11.2 Unstructured personal information

The scrubber replaces structured identifiers that match its recognizers, and the confidentiality theorem is limited to that class. Pattern matching cannot detect unstructured self-disclosure, such as a customer describing a medical condition or identifying landmarks in prose, and recall for structured data depends on the pattern set; deliberately obfuscated forms (digits spelled out, or split across messages) may escape it. Addressing unstructured content without trusting the provider requires a local named-entity-recognition or small scrubbing model inside the Layer 1 perimeter, which would introduce its own error rate and is left for future work.

11.3 Nonce entropy on text-only channels

A four-digit nonce balances usability against guessing resistance. Because it is drawn after the model turn, the planner cannot predict or solicit it, and the three-attempt lockout limits a blind guess to a success probability of 3/9000 ≈ 3.3 × 10−4 per proposal. For high-value transactions the nonce length can be increased to six alphanumeric characters, which gives more than 2 × 109 combinations.

11.4 Residual risks and scope

Several risks lie outside the guarantees stated here. (i) The theorems assume a correct TCB; an implementation fault in Layer 2 or Layer 3, or a business-logic error inside a principal command, is not mitigated by the architecture. (ii) A human principal can approve an accurate card on the basis of a mistaken understanding, and repeated confirmations may cause fatigue. (iii) Plain-text replies in non-mutating turns remain under the planner’s control and may be inaccurate or misleading, although they cannot change state or address other users. (iv) Timing and response-length side channels were not analyzed. (v) The static gates are syntactic and conservative; they do not detect aliasing that bypasses the rules, so they complement, and do not replace, runtime mediation. (vi) Interactions among several cooperating planners are not modeled. (vii) Availability is guaranteed relative to the planner only; the deterministic path can still be disrupted by network or infrastructure attacks and by flooding of its own endpoints.

11.5 Empirical validation

This paper argues for security by construction and states the assumptions under which each invariant holds. It does not report measured attack-success rates, latency overhead, or effects on task utility. Such measurements, obtained from a controlled red-team evaluation with a documented protocol, are the principal item of future work.

12. Conclusion

Treating a language model as a trusted application controller governed by natural-language instructions is incompatible with multi-tenant commercial security. When an agent serves the public, both the external caller and the internal planner must be modeled as untrusted. BRAH demotes the planner from controller to an unprivileged, context-blind advisor inside a three-layer deterministic reference monitor. Availability follows from LLM-Zero Completeness, which gives every business capability a model-free execution path. Integrity follows from context-bound proxies and split-authority proposals, reinforced by turn-level preemption and post-turn nonces, which together remove the confused-deputy and UI-phishing paths. Confidentiality follows from two-tier ingress scrubbing, principal-owned opaque handles, zero-argument introspection, and metadata pseudonymization, which remove disclosure to the provider and cross-user existence oracles for the protected classes of data. Compile-time verification gates in the reference implementation keep these properties from depending on developer discipline. We expect the approach to serve as a baseline for agents that act on behalf of businesses for the public, and we identify controlled empirical evaluation and protection of unstructured personal data as the next steps.
