Byzantine-Resilient Agent Harnesses: Enforcing Availability, Integrity, and Confidentiality When Both the Caller and the LLM Planner Are Untrusted

Omid Baharloo

baharloo.omid@gmail.com

Abstract

Large language model (LLM) agents are increasingly given operational authority over public-facing commercial and organizational services that handle transactions, customer records, and business state. Existing defenses either rely on model alignment and prompt-level instructions, or assume a personal-assistant setting in which the party issuing instructions is a trusted owner. In public service deployments neither assumption holds: any anonymous caller may be an adversary, and the LLM planner itself, which is subject to stochastic failure, adversarial manipulation, and observation by its hosting provider, must be treated as an untrusted component. We present the Byzantine-Resilient Agent Harness (BRAH), an architecture that enforces availability, integrity, and confidentiality without depending on model compliance. BRAH rests on three mechanisms. First, LLM-Zero Completeness requires that every business state transition reachable through natural-language interaction is also reachable through a deterministic, model-free port state machine, so that service continues during a total model outage or budget exhaustion. Second, policy-partitioned split authority and context-bound proxies bind every identity parameter from an immutable execution context and partition state-mutating capabilities according to the service designer’s risk policy into direct context-bound mutations and confirmation-gated proposals ratified out of band by the authenticated principal. Third, bidirectional, principal-owned capability envelopes replace sensitive inputs and outputs with opaque handles in the model’s context across verified platform contacts, pattern scrubbers, and state-machine input boxes, while parameter-free introspection removes existence oracles. We formalize a dual-adversary threat model, state and prove three invariants under explicit assumptions, describe a declarative programming model with compile-time verification gates in a reference runtime, trace four deployment scenarios, and analyze ten classes of attack against the design.

Keywords: LLM agents; prompt injection; reference monitor; confused deputy; object capabilities; capability envelopes; information-flow control; Byzantine fault tolerance

1. Introduction

Large language models have moved from passive text generators to goal-directed agents that perceive digital environments and execute multi-step workflows. In commercial and organizational settings, such agents are given tool interfaces that let them query relational databases, call third-party REST and Model Context Protocol (MCP) endpoints, manage content systems, and mediate transactions over public messaging platforms.

This shift exposes a structural weakness. An autoregressive model receives control instructions and untrusted data in a single, undifferentiated token sequence. Classical systems separate the two by construction: the Harvard architecture, write-xor-execute page permissions, and parameterized database queries all prevent data from being interpreted as code. An LLM offers no corresponding separation between system prompts, developer policy, conversation history, and external content.

1.1 Model alignment is not a security boundary

Most agent frameworks attempt to prevent unauthorized state changes and data leakage through model-level measures: reinforcement learning from human feedback, instruction-hierarchy fine-tuning, defensive system prompts, and secondary LLM-based filters. Benchmarks of tool-integrated agents show that such measures fail under adaptive attack [9, 10]. Direct injection, indirect injection embedded in retrieved pages or database rows [11], multi-turn social engineering, and syntactic obfuscation all bypass prompt-level guardrails with regularity. Requiring a stochastic model to enforce access-control invariants while it interprets adversarial tokens contradicts two established design principles, separation of duty and complete mediation [5].

1.2 Two threat models

Recent work applies software-security techniques, notably information-flow control (IFC) and capability-based enforcement, to LLM agents [6, 7, 8]. These systems are designed for what we call the personal-assistant threat model, which rests on four assumptions. (i) The prompter is a single authenticated, trusted owner. (ii) The adversary is a third party that plants instructions in passive data fetched during execution, such as a document or an email body. (iii) The inference provider is trusted, so confidential documents may be placed in the model context in plaintext. (iv) Availability is secondary to fail-closed behavior, so halting when a policy is violated or the model is unreachable is acceptable.

Public service agents, such as event-registration desks, customer-support agents, content-publishing employees, and automated cloud-provisioning desks, operate under a different model, the public service-agent threat model, in which all four assumptions fail together. Any anonymous user of a messaging network can open a session, so the conversational caller is the primary adversary and may attempt to read other customers’ records, manipulate prices, or trigger unauthorized broadcasts. Because the planner processes the caller’s input directly, and is itself subject to hallucination and jailbreaking, it must be modeled as an untrusted, possibly compromised component. Cloud-hosted inference spans third-party jurisdictions and proxies, so sending regulated personal data or credentials to the model in plaintext is itself a disclosure. Finally, availability is a business requirement: a commercial agent cannot stop working because a provider suffers a network partition, returns gateway errors, or because an abusive caller exhausts the token budget.

1.3 Contributions

Rather than strengthening prompt compliance, BRAH encapsulates the untrusted planner inside a deterministic reference monitor. The contributions are as follows.

  1. A dual-adversary service threat model in which the external caller Acaller and the internal planner ALLM are both untrusted and may collude (Section 3).
  2. LLM-Zero Completeness for availability: every business transition that can be reached through model-assisted interaction has an equivalent path through deterministic ports that never invokes the model (Section 5).
  3. Context-bound proxies and policy-partitioned split authority for integrity: all ambient identity and recipient parameters are injected by the reference monitor, while the service designer partitions state-mutating actions into direct context-bound operations and confirmation-gated proposals ratified by the authenticated principal (Section 6).
  4. Bidirectional, principal-owned capability envelopes for confidentiality: a tokenization vault supporting verified platform contacts, configurable pattern scrubbing, prompted state-machine input boxes for unstructured secrets, and outbound user-egress unveiling, paired with zero-argument introspection to eliminate existence oracles (Section 7).
  5. A declarative programming model with compile-time static checks that make insecure tool definitions unregisterable (Section 8), together with an analysis of four deployment scenarios and ten attack classes (Sections 9 and 10).

2. Background and Related Work

2.1 Classical foundations

BRAH adapts four results from systems security. Anderson’s reference monitor concept [1] requires that a mediating mechanism be tamper-proof, invoked on every access (non-bypassable), and small enough to be verified. Hardy’s confused deputy problem [2] describes how a program holding ambient authority can be induced by a less-privileged caller to misuse it. In a conventional agent, tools whose target parameters (recipient, customer record, or destination channel) are chosen by the model make the agent a confused deputy. Object-capability security [3] removes ambient authority by requiring that a subject hold an unforgeable reference that both designates an object and authorizes a set of operations; BRAH transfers this idea to natural-language runtimes through principal-owned, sink-restricted capability handles. Denning’s lattice model of information flow [4] provides the vocabulary of confidentiality and integrity labels used to reason about flows toward public sinks and from low-integrity sources.

2.2 LLM agent security architectures

Benchmarks such as InjecAgent [10] and AgentDojo [9] show that prompt-level defenses fail against adaptive indirect injection, and recent work has moved toward system-level isolation. CaMeL [6] derives control and data flows from the user’s trusted query. A privileged LLM compiles the query into a restricted program, a quarantined LLM without tool access parses untrusted data into typed values, and a custom interpreter tracks provenance and enforces capability policies at tool calls. The authors report solving 77% of AgentDojo tasks with provable security, against 84% for an undefended system. The guarantee presupposes a trusted initial query; if that query comes from an adversary, the privileged model compiles the attacker’s instructions into the plan. In addition, the quarantined model sees the raw data it parses, and a policy violation causes execution to stop.

FIDES [7] propagates confidentiality and integrity labels dynamically across planner turns and provides a selective hiding primitive that replaces confidential values with symbolic variables in the model context. It assumes a trusted task initiator and does not address out-of-band principal confirmation, bidirectional envelopes for unstructured inputs, or operation when the planner is unavailable. IsolateGPT [8] isolates third-party LLM applications in separate processes mediated by a central hub, which limits cross-application contamination for a single user, but it does not address shared business state manipulated by anonymous external callers.

3. System Model and Threat Model

To state guarantees that do not depend on stochastic model behavior, we model the service agent as a state-transition system mediated by a deterministic reference monitor.

3.1 Notation

A public service agent is the tuple Ssys = ⟨S, P, Γ, C, T_M, M, H, Σ⟩. The set of authenticated principals is S = Suser ∪ Sowner, comprising external end users (customers, registrants, channel subscribers, or programmatic personal assistants) and the service owner (the operator who deploys and supervises the agent).

Events enter through four typed ingress ports, P = {Pbot, Pacct, Papi, Pllm}. The port Pbot carries official messenger-bot webhooks, which deliver verifiable sender identifiers, structured contact cards, and inline-button callback payloads. The port Pacct carries personal-account session streams (for example MTProto-based clients or WhatsApp session gateways), which deliver text and media messages authenticated by platform peer identifiers but offer no structured interface elements. The port Papi carries structured HTTP and MCP endpoints, authenticated by bearer tokens whose SHA-256 digests are stored server-side. The port Pllm is the untrusted output stream (text and tool calls) returned by the inference gateway.

On an event from any port p ∈ P ∖ {Pllm}, the harness creates an immutable execution context bound to a turn:

Γ = ⟨run_id, port, peer_id, role, σdb⟩
(1)

where peer_id is the identity of the caller as verified by the transport, role ∈ {user, owner} is the caller’s role, and σdb is the database state snapshot. The context is held in coroutine-local runtime storage. The planner M has no read or write access to Γ and cannot forge or override any of its fields.

The domain engine exposes a finite set of deterministic commands C = Cread ∪ Cmutate. The service designer partitions state-mutating commands according to their business risk and user-experience requirements into two disjoint subsets,

Cmutate = Cmutatedirect ∪ Cmutateconfirm
(2)

where Cmutatedirect contains low-risk, reversible mutations that the designer permits the planner to invoke directly on behalf of the current caller (for example registering in an open course or opening a support ticket), and Cmutateconfirm contains high-consequence or irreversible mutations that require out-of-band confirmation by the user or the service owner (for example canceling a registration, finalizing a paid order, or publishing to an external channel). Each command c ∈ C is guarded by a deterministic predicate Authz(s, Γ, c, args) ∈ {true, false}.

The untrusted planner is a function M : Hsan × T_M → Text ∪ Aproxy. It receives only a sanitized, pseudonymized history Hsan and an attenuated proxy toolset T_M. Each proxy tool t̃ ∈ T_M either executes a context-bound operation in Cread ∪ Cmutatedirect or emits a non-executing proposal Π(c, args) for some c ∈ Cmutateconfirm. The reference monitor H mediates every ingress event, model invocation, and egress side effect. It maintains the opaque capability envelope vault

Σ : R → Vsecret × Kind × OwnerPeer × 2T
(3)

which maps unguessable handle strings h ∈ R to the underlying sensitive values, together with the owner peer and the set of sinks (database writes, owner notifications, or user egress) permitted to dereference each handle.

3.2 Dual-adversary model

The first adversary, the untrusted external caller Acaller, interacts over Pbot, Pacct, or Papi and controls all inbound payloads. It may send direct injections, spoof system roles, or embed instructions in forwarded messages, documents, or URLs. Its goals include cross-peer access (peer_id′ ≠ Γ.peer_id); unauthorized mutations such as registering without payment, obtaining discounts outside the owner’s negotiation limits, or forging payment confirmations to the owner; and sending messages to third parties. It may also mount denial-of-wallet attacks by flooding the agent with token-intensive requests to exhaust the service’s inference quota.

The second adversary is the Byzantine planner [12] ALLM, which represents the model together with its hosting infrastructure in two roles. As an active subverter, whether through Acaller’s injections, poisoned weights, or ordinary hallucination, the model may emit arbitrary tool calls with fabricated arguments, supply another user’s identifier or handle, produce deceptive text next to a legitimate confirmation control, or claim that an operation has completed. As a passive observer, the cloud provider, network relays, and logging pipelines can read every token of the prompt. Any plaintext personal data, credential, or platform identifier in the prompt is therefore assumed to be disclosed. The two adversaries may collude.

We assume that transport-level authentication (Layer 1) is not compromised, that the reference monitor and the domain engine are correctly implemented, and that cryptographic primitives and the random-number generator behave as specified.

3.3 Security objectives

A harness is Byzantine-resilient if it enforces three invariants under this model.

Availability invariant (A). Every domain command c ∈ C assigned to a principal role remains executable, with latency bounded independently of M, when M returns arbitrary errors, times out, or is unreachable.

Integrity invariant (I). No command c ∈ C and no outbound transmission can be executed by M for any principal other than Γ.peer_id. Moreover, no confirmation-gated command c ∈ Cmutateconfirm can be executed by M directly; every transition in Cmutateconfirm requires an explicit confirmation originating from the authorized principal over a deterministic port, with all identity parameters bound from Γ.

Confidentiality invariant (C). For all data kinds configured as confidential envelopes in Vsecret (Section 7), the mutual information between the prompt observed by M and Vsecret is zero, I(Prompt; Vsecret) = 0, and no caller s can infer or dereference any datum owned by a principal s′ ≠ s.

4. Architecture

BRAH replaces the usual topology in which the model acts as controller with a three-layer reference monitor. The planner is an advisory leaf node outside the trusted computing base (TCB). Figure 1 shows the layers and the data crossing each boundary.

4.1 Layer 1: ingress authentication, port normalization, and envelope capture

Layer 1 terminates network connections from messaging servers and API clients and performs three operations before any downstream logic runs. First, it authenticates at the transport level. For bot webhooks it validates a secret path component or header known only to the harness and the messaging platform and extracts the unforgeable sender identifier, any button callback payload, and any verified contact card. For personal-account streams it binds the sender’s platform peer identifier to the account session. For structured API and MCP ports, authentication middleware extracts the bearer token, computes its SHA-256 digest, compares it with the stored digest, and rejects failures with 401 Unauthorized before any tool function is reached.

Second, Layer 1 intercepts deterministic triggers. If an authenticated event is an inline-button callback, a slash command, a numeric state-machine code (including a confirmation nonce), or a prompted confidential input box, the model is bypassed and the event is handled deterministically. Third, if the event is free text destined for the model, Layer 1 applies the configured ingress scrubbers (Section 7.1), replacing structured contact payloads and pattern-matched sequences with opaque handles h ∈ R stored in Σ.

4.2 Layer 2: reference monitor and context binder

Layer 2 is the core of the TCB. It instantiates Γ and enforces three mediation rules. Implicit context binding: whenever a tool or command is invoked, Layer 2 reads peer_id and role from Γ and injects them into the function’s typed context parameter. These fields do not appear in the schema presented to the model, so the model cannot specify or alter recipient or customer boundaries. Policy confirmation gate: direct principal triggers arriving on Pbot, Pacct, or Papi may invoke any authorized command in C, while calls originating from Pllm are restricted to context-bound operations in Cread ∪ Cmutatedirect and non-mutating proposal generators Π(c, args) for c ∈ Cmutateconfirm. Scoped envelope dereferencing: before any handle argument reaches Layer 3 or is unveiled at egress, Layer 2 checks it against Σ, verifying that it is owned by the current caller and is permitted for the target sink (Equation 5).

4.3 Layer 3: deterministic domain engine

Layer 3 contains the domain logic, persistence models, pricing rules, and outbound notification routers. It contains no model calls. Its inputs are commands whose parameters were validated and bound by Layer 2, and its outputs are state changes, outbound envelopes, and notifications generated by code.

4.4 Owner supervision and out-of-band operator approvals

In addition to end-user interactions, a service agent requires supervision by its owner. Rather than relying on conversational instructions to the model, administrative actions—such as updating operational parameters, inspecting database records, or approving high-consequence actions—occur over deterministic channels. When a command in Cmutateconfirm requires owner ratification (for example approving a manual payment receipt or authorizing a public broadcast), Layer 3 dispatches a deterministic approval card carrying signed inline buttons to the owner’s authenticated messaging chat. Because Layer 1 verifies that the callback originates from the configured owner identifier before executing the transition, neither an external caller nor a compromised planner can forge owner approval.

5. Pillar I: Availability through LLM-Zero Completeness

A common failure mode in agent engineering is LLM-monolithic coupling, in which the model sits on the critical path of every interaction. If the provider is unavailable, throttles requests, or responds slowly, or if an attacker consumes the service’s token budget, such an agent stops responding altogether. For a commercial service this is a violation of basic availability requirements.

5.1 Definition

Definition 1 (LLM-Zero Completeness). Let Σbiz denote the domain state space of the service and let Δ : Σbiz × C → Σbiz be the deterministic transition function over commands. A harness satisfies LLM-Zero Completeness if and only if, for every reachable transition σ c→ σ′ that can be assisted or proposed by the planner M, there is a finite input sequence p over the deterministic ports Pdet = Pbot ∪ Pacct ∪ Papi that produces the same transition without invoking M:

∀(σ, c) ∈ Σbiz × C,  ∃  p ∈ Pdet*    such that    Exec(p, σ) = Δ(σ, c) ∧ Calls(M) = 0
(4)

Under this definition the model is never the exclusive executor of a business capability. Its role is to help users who write in natural language discover commands and fill their parameters for operations that remain executable without it.

5.2 Deterministic port state machines

Because transports differ in their interface primitives, Layer 1 implements one deterministic port state machine (port-FSM) per port class, each exposing the full command set without invoking M. On bot ports, every user-facing command is compiled into an interactive menu button and a slash-command handler. In an event-registration agent, for example, the menu offers buttons for event details and remaining capacity, a verified FAQ, registration, sharing a verified contact, and payment. Each button produces a signed callback that Layer 1 routes directly to Layer 3.

On personal-account channels, which have no inline buttons, Layer 1 maintains a per-peer finite-state automaton driven by numeric codes or keywords. Sending 0 returns a numbered directory of services, and replying with a number advances a deterministic dialogue that collects the required fields and confirms high-consequence actions with a four-digit nonce. On structured API and MCP ports, every capability is a typed JSON-RPC tool that deterministic scripts or external personal assistants can call without conversational mediation.

5.3 Unified command bus

Dual-mode systems risk logic divergence between manual menus and model-assisted flows. BRAH removes the risk by routing all execution paths through a single command bus in Layer 3. A registration may be triggered by an inline menu button, by a numeric wizard, by a programmatic call from a personal assistant, by a direct context-bound model call (when configured in Cmutatedirect), or by confirming a card that the model proposed (when configured in Cmutateconfirm). All paths invoke the same Layer 3 handler, so authorization, validation, and side effects are implemented once.

5.4 Circuit breaker and quotas

When a user sends free text instead of a menu command, Layer 2 mediates the call to M behind two guards. First, a circuit breaker traps model failures. If the gateway exceeds a timeout (8 s in the reference configuration), returns a 5xx or 429 status, or produces output that fails schema validation, Layer 2 replies with the deterministic menu and a notice that natural-language assistance is temporarily unavailable. Second, per-peer sliding-window quotas bound token consumption by a single caller: at most NLLM natural-language turns per hour (15 in the reference configuration) and at most Ktools proxy calls per turn (4). When a peer exceeds NLLM, Layer 1 switches that peer’s session to menu-only mode, which stops model token consumption while leaving every command available. A legitimate customer who reaches the limit can therefore still complete registration and payment.

5.5 Availability theorem

Theorem 1 (Availability under planner failure). Consider a service agent built on BRAH that satisfies Definition 1, and assume that the deterministic components (transports, Layers 1 to 3, and the database) are available. For any failure state of the planner M, including complete disconnection, arbitrary malformed output, or per-peer quota exhaustion, the set of executable transitions Δ(σ, c) for all authorized principals is unchanged, and each is reachable within a time bound that does not depend on M.

Proof. Take any authorized command c ∈ C and state σ ∈ Σbiz. By Definition 1, the command compiler has registered a deterministic trigger sequence p ∈ Pdet* mapped to c on the command bus. When principal s submits p through a bot callback, a numeric code, or an API call, Layer 1 authenticates s, matches p against a trigger table in O(1) time, and dispatches c through Layer 2 to Layer 3 without invoking M. If instead s submits free text while M is unreachable, malformed, or rate-limited, Layer 2 traps the fault within the timeout and returns the menu that lists p. In both cases s executes Δ(σ, c) with Calls(M) = 0. ■

The theorem concerns the model as a point of failure. It does not protect against failures of the deterministic components, which are part of the TCB and are addressed by conventional redundancy. The coverage premise of Definition 1 is checked at build time (rule AST-04, Section 8.3).

6. Pillar II: Integrity through Context-Bound Proxies and Policy-Partitioned Split Authority

Integrity requires that no cross-user state change, unauthorized financial charge, or cross-user communication can occur even when an attacker has complete control over the model’s output.

6.1 The confused deputy in agent tool execution

Conventional tool-calling frameworks expose general-purpose functions to the model, for example send_message(chat_id, text), cancel_registration(user_id), or register_user(user_id, name, phone). The harness holds the global credentials, so every parameter in a tool’s schema is under the model’s control. After an injection, the subverted model can supply another user’s chat_id or user_id, and the harness executes the request with its own ambient authority. This is the confused deputy [2].

6.2 Context-bound capability proxies

BRAH forbids ambient target parameters in the planner’s toolset: no tool exposed to M may accept a parameter that designates a message recipient or principal identity (chat_id, peer_id, user_id, customer_id, recipient). The model has no message-sending tool at all: its ordinary text output is the reply to the current caller, and it otherwise receives narrow proxies such as search_kb(query) and context-bound domain commands. When M calls a proxy, Layer 2 reads the context Γ and rewrites the call deterministically:

check_my_status()  →  SELECT * FROM registrations WHERE peer_id = Γ.peer_id
output(M) = m  →  transport.send_text(recipient = Γ.peer_id, text = egress_Σ(redact(m)))

Because M cannot alter Γ, a prompt-injected model has no means of addressing a message to another user or reading or mutating another caller’s records.

6.3 Policy-partitioned split authority: direct vs. confirmation-gated mutations

Different state mutations carry different operational risks and user-experience trade-offs. In an event-registration service, for instance, a service designer may wish to allow the conversational agent to execute an initial course registration directly once the caller provides their name and contact handle (c ∈ Cmutatedirect), avoiding confirmation friction, while requiring explicit out-of-band confirmation before canceling an existing registration or committing a financial payment (c ∈ Cmutateconfirm).

BRAH supports this distinction directly in the reference monitor:

  • For commands declared in Cmutatedirect (mode="direct"), the runtime exposes a context-bound proxy to M. When invoked, Layer 2 binds ctx.peer_id from Γ, validates the ownership of any capability handles in Σ, and executes Δ(σ, c) for the current caller only. Even if M is subverted, its effect is strictly confined to Γ.peer_id’s own session state.
  • For commands declared in Cmutateconfirm (mode="user_confirm" or mode="owner_confirm"), direct execution is withheld from T_M. Instead, the runtime synthesizes a proposal tool propose_<c>(args), the proposal Π(c, args). Calling it changes no domain state: Layer 2 validates the arguments, computes any monetary quote in deterministic code, stores an inert proposal record, and renders a confirmation control to the authenticated principal (either the caller or the service owner). The mutation Δ(σ, c) is executed in Layer 3 if and only if that principal activates the confirmation button (on Pbot) or returns the post-turn nonce (on Pacct).

6.4 What-you-see-is-what-you-sign binding and turn preemption

An early design let the model emit free text together with a button-rendering tool. That allowed UI phishing (attack class I-1): a subverted model could write “Click below to download the free brochure” above a button that cancels a registration or commits a paid order. It also allowed the model to alter draft fields before confirmation (class I-3).

BRAH closes both paths with WYSIWYS draft binding and turn-level message preemption. Whenever M calls a proposal tool, Layer 2 discards all free text that M produced in that turn, so the model cannot frame or disguise the confirmation. Layer 2 then builds the entire confirmation message and button label deterministically from the stored proposal record and the pricing engine. The card begins with a fixed header (“Official confirmation form: the button below finalizes the details listed here”), lists every bound parameter (full name, masked phone preview, exact price), and carries a descriptive button label such as “Confirm cancellation of registration” or “Confirm registration: price 2,000,000 units”. Generic labels such as “OK” are rejected by the command compiler.

6.5 Post-turn egress nonces on text-only channels

On personal-account channels there are no inline buttons. If confirmation used a static code (“send 9 to confirm”), a prompt-injected model could use its text reply to socially engineer the user (“to receive a free gift, reply 9”) into authorizing a mutation.

BRAH instead uses dynamic post-turn egress nonces. When M calls a proposal tool on such a channel, Layer 2 ends the model turn immediately. Only after the turn has finished does Layer 2 draw a fresh nonce from a cryptographic generator,

nauth ←R {1000, …, 9999}

store ⟨prop_id, nauth, expires_at = t + 300 s, attempts = 0⟩, and append a system footer to the card at the egress boundary (“[System]: to finalize this action, send the code 4829”). The nonce is never written to the conversation history visible to M, so the planner has no information about it. Three consecutive wrong inputs invalidate the proposal, which limits guessing.

6.6 Separating system-fact notifications from customer escalations

If the agent has a general tool for messaging the owner’s notification channel, a compromised model can fabricate a payment or registration confirmation during a customer conversation and thereby induce the owner to deliver goods or services without payment (class I-2). BRAH therefore separates the two kinds of message. Official notifications of state changes, such as confirmed registrations or verified payments, are emitted only from Layer 3 command handlers after the database commit, and the planner has no tool that can produce one. To let the agent hand an unanswerable question to the owner, the planner is given only escalate_to_owner(summary). That tool is limited to one open escalation per customer thread, and Layer 2 prefixes every escalation with a fixed banner stating that the text is an unverified claim by the customer and carries no system or financial confirmation.

6.7 Integrity theorem

Theorem 2 (Integrity against planner subversion). Consider a service agent that implements context-bound proxies, policy-partitioned split authority, WYSIWYS turn preemption, and post-turn egress nonces, and assume that Layer 1 transport authentication is not compromised. Then: (1) the probability that an active Byzantine planner M mutates a record or transmits a message belonging to a peer peer_id′ ≠ Γ.peer_id is 0 across all commands c ∈ C; and (2) for any confirmation-gated command c ∈ Cmutateconfirm, the probability that M executes c without principal confirmation is 0 on Pbot and Papi, and at most 3/9000 ≈ 3.3 × 10−4 per proposal on Pacct.

Proof. (1) For every tool t̃ ∈ T_M (including direct commands in Cmutatedirect), recipient and principal identifiers are absent from the schema and are bound by Layer 2 from Γ.peer_id, so the probability of a cross-peer dispatch or cross-peer state mutation is 0. (2) Since Cmutateconfirm ∩ T_M = ∅, the planner can only invoke Π(c, args) for c ∈ Cmutateconfirm. On each such call, Layer 2 discards the planner’s free text and emits a deterministic WYSIWYS card. On Pbot and Papi, executing c requires an authenticated callback bound to the principal’s session, which M cannot produce, so the probability is 0. On Pacct, execution requires the principal to return nauth, which is drawn after the planner’s turn has ended. Hence I(M; nauth) = 0, and turn preemption removes any concurrent text through which M could solicit a code. Any code that M causes to be submitted must therefore be a blind guess, and with a lockout after three attempts the probability of matching a uniformly drawn four-digit nonce is at most 3/9000. ■

7. Pillar III: Confidentiality through Bidirectional Capability Envelopes

Confidentiality requires that sensitive user data and service secrets designated by the service designer remain hidden from other callers (Acaller) and from the cloud model provider (ALLM). Because different domains treat different attributes as confidential—for example, one service may require postal addresses and national identifiers to be hidden from the model while another requires outbound license keys or access links to be delivered without entering the prompt—BRAH provides a policy-driven, bidirectional capability envelope mechanism.

7.1 Three-mode inbound envelope capture

For every input data kind configured by the service designer as an inbound envelope, Layer 1 captures the value before prompt construction through one of three deterministic channels:

Mode 1 (Platform-verified contact cards): When a user presses the messaging platform’s native contact-sharing button (kind phone_verified) and Layer 1 verifies that the contact card’s user identifier matches the authenticated sender, Layer 1 intercepts the structured payload outside the model, stores the number in the vault Σ, and inserts a synthetic event into the transcript carrying only the handle.

Mode 2 (Configurable pre-prompt pattern scrubbing): For structured identifiers enabled in the service’s envelope policy (such as phone_unverified, national_id, card, iban, or credentials), Layer 1 normalizes decimal digits across Latin, Arabic-Indic, and Extended Arabic-Indic Unicode blocks and scans inbound free text before logging or model transit. Each match is stored in Σ and replaced inline by a typed handle (for example, “my number is [h_phone_unverified_u3b1]”). If a command requires a phone_verified handle, Layer 2 rejects a phone_unverified handle and instructs the planner to request a verified contact card.

Mode 3 (FSM-prompted envelope boxes for unstructured data): Regular expressions cannot reliably segment unstructured personal data such as a street address, a medical note, or a custom passphrase inside free text. When a command requires an unstructured envelope kind (for example HandleRef["address"]), the planner invokes request_envelope_input(kind="address") (or the user selects the corresponding menu button). Layer 1 transitions the caller’s port-FSM to AWAITING_ENVELOPE(kind) and prompts the caller. On the caller’s next message, Layer 1 intercepts the entire payload before the model is invoked, seals the plaintext in Σ as h_address_..., resets the FSM to IDLE, and passes only the opaque handle to the planner.

7.2 Principal-owned, sink-typed capability handles and outbound envelopes

A naive tokenization scheme that keeps a flat table from handle to plaintext is vulnerable to confused handle injection (class C-1). If user B learns or guesses a handle that belongs to user A and asks the model to act on it, a tool wrapper that dereferences the handle discloses or corrupts A’s record. BRAH defines each vault entry as a four-tuple object capability,

Σ(h) = ⟨vplaintext, kind, owner_peer, Psinks⟩

and Layer 2 applies the following dereferencing rule whenever a component attempts to resolve h for sink τ under context Γ:

{
Dereference(h, Γ, τ) = vplaintext   if Σ(h).owner_peer = Γ.peer_id ∧ τ ∈ Σ(h).Psinks
Dereference(h, Γ, τ) = ⊥ (raise HandleAccessViolation)   otherwise
(5)

The sink set Psinks governs both inbound and outbound envelopes:

  • For an inbound envelope (user to service), Psinks = {db, owner_notify}. The handle can be unveiled into a Layer 3 database write or an owner notification, but never into a tool result returned to M.
  • For an outbound envelope (service to user, such as a minted cloud access token, a license key, or a destination payment card number), Layer 3 seals the generated value in Σ with owner_peer = Γ.peer_id and Psinks = {user_egress}, returning only the handle h to M. When M includes h in its reply to the caller, Layer 2 verifies Equation (5) for τ = user_egress, substitutes vplaintext on the outbound network transport to Γ.peer_id, and records only a masked placeholder in the conversation history Hsan so that subsequent model turns never observe the secret.

7.3 Zero-argument state introspection

Scrubbing and ownership checks still leave a side channel, the existence oracle (class C-4). Suppose a customer-facing tool accepts a phone handle, as in check_registration_status(phone_handle). An attacker types a victim’s number into the chat, Layer 1 turns it into a handle owned by the attacker’s own session, and the model passes the handle to the tool, which reveals whether the victim is registered.

BRAH eliminates the oracle by requiring that customer-facing status tools take no identity or handle argument (check_my_status()). Layer 2 binds the query to the caller’s authenticated transport identity (WHERE peer_id = Γ.peer_id).

7.4 Deterministic metadata pseudonymization

Platform-native identifiers (chat, user, and channel identifiers) are also withheld from the planner, since they allow correlation across sessions. Layer 2 removes them before building the prompt and substitutes constant symbolic names (CURRENT_USER, CURRENT_OWNER). Outbound tool calls resolve these symbols to physical identifiers only inside Layer 2’s egress adapter.

7.5 Confidentiality theorem

Theorem 3 (Confidentiality and non-interference). Consider a service agent that implements three-mode inbound envelope capture, principal-owned sink-typed handles (including outbound user-egress unveiling), zero-argument introspection, and metadata pseudonymization. Let Vsecret denote all values captured by the configured inbound and outbound envelope channels together with platform identifiers. Then (1) no value in Vsecret enters the context window of M, and (2) for any two distinct end users u1 ≠ u2, the observable outputs of u1 do not depend on the private records or handles of u2.

Proof. (1) Every inbound envelope value is intercepted at Layer 1 (by contact-card extraction, pattern scrubbing, or the AWAITING_ENVELOPE state machine) before prompt construction, and every outbound envelope value is sealed in Layer 3 and unveiled by Layer 2 only on the wire after M’s turn while persisting a masked placeholder in Hsan. Because handles are drawn from a cryptographic random generator independently of the plaintext, I(Prompt; Vsecret) = 0. (2) Suppose u1 tries to dereference or unveil a handle h2 created in u2’s session. The attempt fails Equation (5) because Σ(h2).owner_peer = u2 ≠ Γ.peer_id = u1. Suppose u1 tries to probe u2’s registration state. Customer-facing status tools take no identity arguments and filter on peer_id = u1. The outputs available to u1 are therefore independent of the state of u2. ■

8. Declarative Programming Model and Static Verification

Security architectures often fail in practice because they depend on application developers to write permission checks by hand in every tool function. In BRAH the invariants are enforced by the framework’s compiler and runtime, so that an insecure tool cannot be registered. The reference implementation is called codo-core.

8.1 Unified capability declarations

Developers declare every capability with a single decorator whose mode states the designer’s authority policy (read, direct, user_confirm, owner_confirm, menu_only) and whose signature states any envelope parameters (HandleRef[Kind]):

from codo_core import ActionCtx, HandleRef, ReadCtx, action

@action(
    mode="direct",                  # Designer policy: direct context-bound execution
    title_fa="Register in course",
    menu_button_fa="Register in course",
    humanoid_menu_key="1",
    labels_fa={"full_name": "Full name"},
)
async def register_attendee(
    ctx: ActionCtx,
    full_name: str,
    phone: HandleRef["phone_verified"],
    address: HandleRef["postal_address"],
) -> dict:
    async with ctx.session() as s:
        s.add(Registration(
            customer_id=ctx.customer_id,          # bound from Γ, never from M
            full_name=full_name,
            phone_number=await ctx.unveil(phone),   # Σ: owner, sink and kind checked
            postal_address=await ctx.unveil(address),
        ))
    return {"status": "registered"}

@action(
    mode="user_confirm",            # Designer policy: user confirmation button/nonce
    title_fa="Cancel course registration",
    menu_button_fa="Cancel registration",
    humanoid_menu_key="2",
)
async def cancel_registration(ctx: ActionCtx) -> dict:
    async with ctx.session() as s:
        await s.execute(delete(Registration).where(
            Registration.customer_id == ctx.customer_id))
    return {"status": "canceled"}

@action(mode="read")                # read-only helper: attenuated context
async def search_event_faq(ctx: ReadCtx, query: str) -> list[dict]:
    return await ctx.search_kb(query)

From each @action declaration the framework synthesizes the corresponding security artifacts. Under Pillar I, it mounts a deterministic menu button on Pbot, binds the numeric menu key on Pacct, and drives a deterministic wizard that asks for each parameter by its declared label. Under Pillar II, for mode="direct" it exposes a context-bound proxy that executes for the caller bound in Γ; for mode="user_confirm" it withholds direct execution and generates propose_cancel_registration(); for mode="owner_confirm" the same proposal is routed to the owner’s out-of-band channel; mode="read" functions receive an attenuated context that can neither write, send, nor open envelopes, and their database session always rolls back, enforcing WYSIWYS rendering and post-turn nonce verification. Under Pillar III, Layer 2 verifies before execution that phone and address resolve in Σ to handles of the required kinds owned by ctx.peer_id.

8.2 Typed context injection and schema omission

To build the tool schema for T_M, the framework inspects each function signature, removes the leading context parameter (ReadCtx or ActionCtx), and converts every HandleRef[Kind] annotation into a string handle parameter carrying the pattern ^h_[a-z0-9_]+_[0-9a-f]{16}$. At call time Layer 2 injects the context from the coroutine-local variable. The omitted identity parameters therefore do not exist from the model’s point of view.

8.3 Static verification gates

At build and test time, the checker parses each source file into an abstract syntax tree and enforces the mandatory rules of Table 2.

AST-01, AST-02, AST-03, AST-06 and AST-07 establish the premises of Theorems 2 and 3 at the level of code, AST-04 establishes the coverage premise of Definition 1, and SEC-01 keeps deployment credentials out of any repository that may later be shared or forked.

8.4 Prompt-based enforcement is not accepted as evidence

The development process applies a corresponding rule to security requirements. Each threat in a project’s threat register must be mapped to a deterministic mechanism in Layer 1, 2, or 3 and to an automated test. An entry whose stated enforcement is “prompt” or “model instructions” for a confidentiality, integrity, or availability requirement is treated as unmet. When a developer configures a high-consequence action with mode="direct", the tooling issues an explicit warning describing the trade-off and records the designer’s decision.

9. Case Studies

To show that the design applies across diverse service roles without special-casing, we trace it through four deployment scenarios.

9.2 Scheduled content publication

The second scenario is a news-reporting agent that wakes on schedules, fetches articles from external feeds, writes posts for a companion WordPress site, and publishes summaries to the owner’s messaging channels. Fetched web pages are untrusted and may contain indirect injections intended to make the agent publish a malicious link or post without authorization. Fetched content is wrapped in randomized delimiter tags, output is constrained to a typed schema in which every citation URL must belong to the set of URLs actually fetched in that run, and the publishing command accepts no destination argument: Layer 3 reads destination channels and publishing credentials from the agent’s environment configuration. When the owner configures publication as confirmation-gated (owner_confirm), Layer 3 sends each draft to the owner’s chat with deterministic [Approve & Publish] and [Reject] inline buttons.

9.3 Customer support over personal-account channels

The third scenario is a support agent operating on the business’s own personal messaging accounts, with inbound-message debouncing (a short quiet window with a hard cap). Layer 1 binds each turn to (platform, peer_id). The conversation history the planner sees is rebuilt each turn from the bound conversation only, and the planner’s reply is delivered only to the bound peer, so no tool or reply path can reach another customer. When the business owner replies to a customer directly from the shared account, Layer 1 detects an outbound message not authored by the harness and pauses automated replies on that thread so the owner can converse without interference.

9.4 Automated cloud credential provisioning via outbound envelopes

The fourth scenario is an infrastructure-provisioning agent that sells managed cloud deployment tokens to developers over messaging platforms. A buyer selects a plan and completes payment via an electronic wallet or receipt verification. Once Layer 3 verifies payment deterministically, it calls an internal provisioning endpoint to mint a fresh bearer token (wks_...) and proxy credential. Because the minted token grants deployment access, it must never enter the LLM planner’s prompt or conversation history. Layer 3 therefore seals the credentials inside an outbound capability envelope (Psinks = {user_egress}, Section 7.2) and returns only the handle h_cloud_token_.... Layer 2 unveils the token exclusively on the outbound transport to the authenticated buyer while recording a masked placeholder in the stored chat transcript.

10.1 Interactions among defenses

Three interactions between mechanisms deserve explicit discussion. The first concerns integrity and confidentiality (C-1, C-2, C-4). Consider an architecture that scrubs phone numbers (C-2) but has neither principal-owned handles (C-1) nor zero-argument introspection (C-4). When an attacker types a victim’s number, the scrubber converts it into a handle owned by the attacker’s session. If the status tool accepted a phone handle, the ownership check Σ(h).owner_peer = Γ.peer_id would pass, because the attacker typed the digits in the attacker’s own session. Two measures together close the oracle: typed digits are labeled phone_unverified and cannot be used where verified contact ownership is required, and status queries are bound to Γ.peer_id instead of to any handle.

The second concerns turn-level preemption (I-1, I-3). Common human-in-the-loop frameworks allow the model to emit an explanatory string in the same turn as a deferred approval request. A subverted model can use that string to misdescribe what approval does. By suppressing the model’s text whenever a proposal is emitted and generating the whole card from the validated proposal, BRAH ensures that the principal sees only system-generated parameters.

The third concerns quotas and completeness (A-1, A-2). In a conventional chatbot, rate-limiting a user after a number of messages can block a legitimate customer from completing a purchase. Because BRAH satisfies LLM-Zero Completeness, switching a rate-limited session to menu-only mode never blocks a conversion: the customer still has the deterministic menu for registration and payment, at no token cost.

11. Discussion and Limitations

11.1 Designer-tunable confirmation policy versus fail-safe defaults

Requiring out-of-band confirmation before a state mutation introduces an additional user interaction step. Rather than imposing a one-size-fits-all mandate, BRAH makes the confirmation boundary a declarative per-capability parameter (mode) while enforcing context binding (Γ.peer_id) and capability-envelope ownership (Σ) unconditionally across both direct and confirmation-gated commands. Service designers can therefore choose direct execution for low-risk, reversible actions where conversational speed matters, and reserve WYSIWYS confirmation buttons or post-turn nonces for destructive, irreversible, or financial commitments.

11.2 Structured versus prompted unstructured envelopes

While pre-prompt pattern scrubbers automatically capture structured identifiers (such as phone numbers, national identifiers, and card numbers), unstructured confidential fields (such as street addresses or passphrases) require the caller to enter them after Layer 1 activates an AWAITING_ENVELOPE state-machine prompt. If a caller unexpectedly volunteers an unstructured secret inside an ordinary free-text turn before the envelope prompt is activated, pattern matching alone cannot guarantee its detection without a local named-entity classifier inside Layer 1.

11.3 Nonce entropy on text-only channels

A four-digit nonce balances usability against guessing resistance. Because it is drawn after the model turn, the planner cannot predict or solicit it, and the three-attempt lockout limits a blind guess to a success probability of 3/9000 ≈ 3.3 × 10−4 per proposal. For high-value transactions the nonce length can be increased to six alphanumeric characters, which gives more than 2 × 109 combinations.

11.4 Residual risks and scope

Several risks lie outside the guarantees stated here. (i) The theorems assume a correct TCB; an implementation fault in Layer 2 or Layer 3, or a business-logic error inside a domain command, is not mitigated by the architecture. (ii) A human principal can approve an accurate card on the basis of a mistaken understanding, and repeated confirmations may cause fatigue. (iii) Plain-text replies in non-mutating turns remain under the planner’s control and may be inaccurate or misleading, although they cannot change confirmation-gated state or address other users. (iv) Timing and response-length side channels were not analyzed. (v) The static gates are syntactic and conservative; they complement, and do not replace, runtime mediation. (vi) Availability is guaranteed relative to the planner only; the deterministic path can still be disrupted by network or infrastructure outages.

11.5 Empirical validation

This paper argues for security by construction and states the assumptions under which each invariant holds. It does not report measured attack-success rates, latency overhead, or effects on task utility. Such measurements, obtained from a controlled red-team evaluation with a documented protocol, are the principal item of future work.

12. Conclusion

Treating a language model as a trusted application controller governed by natural-language instructions is incompatible with public commercial security. When an agent serves external callers, both the caller and the internal planner must be modeled as untrusted. BRAH demotes the planner from controller to an unprivileged, context-blind advisor inside a three-layer deterministic reference monitor. Availability follows from LLM-Zero Completeness, which gives every business capability a model-free execution path. Integrity follows from context-bound proxies and policy-partitioned split authority, reinforced by turn-level preemption and post-turn nonces, which together eliminate cross-peer confused-deputy attacks and UI phishing while letting the service designer choose which mutations require explicit confirmation. Confidentiality follows from bidirectional principal-owned capability envelopes—spanning verified contacts, pattern scrubbers, FSM-prompted input boxes, and outbound user-egress unveiling—together with zero-argument introspection and metadata pseudonymization. Compile-time verification gates in the reference implementation keep these properties from depending on developer discipline.
